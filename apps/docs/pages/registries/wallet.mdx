# Wallet Registry

Permanently registers stolen wallet addresses on-chain. Once registered, a wallet is marked as compromised and cannot be removed.

**Who can submit:** Individuals (self-attestation with EIP-712 signatures) and DAO-approved operators (batch submissions via OperatorSubmitter).

## EOA Addresses Only

The Wallet Registry is designed for **externally owned accounts (EOAs)** — standard private-key-controlled addresses. Smart contract wallets (Safe, ERC-4337 accounts, etc.) are not meaningful candidates for stolen wallet registration for two reasons:

1. **Key recovery exists.** Smart contract wallets typically support social recovery, guardian rotation, or owner swaps. A compromised key does not permanently compromise the account — the owner can rotate signers and regain control. Marking such an address as permanently stolen is misleading.
2. **Signature verification is EOA-only.** The two-phase registration flow uses `ECDSA.recover` to verify that the wallet owner signed the EIP-712 messages. This only works with secp256k1 signatures (EOAs). Smart contract wallets use [EIP-1271](https://eips.ethereum.org/EIPS/eip-1271) (`isValidSignature`), which the registry does not implement — so smart contract wallets cannot complete the individual registration flow.

:::info
Operator and cross-chain registration paths bypass signature verification and could technically register any address. Operators are DAO-approved entities expected to exercise judgment about which addresses are appropriate to register.
:::

## Storage

```solidity
mapping(bytes32 => WalletEntry) private _wallets;
```

The storage key is derived from CAIP-10 / CAIP-363 wildcard format. For EVM wallets, the key is:

```solidity
keccak256(abi.encodePacked("eip155:_:", wallet))
```

The wildcard `_` means an EVM wallet registered on any chain is marked as compromised across **all** EVM chains. A wallet stolen on Base is also flagged on Optimism, Arbitrum, etc.

## WalletEntry

```solidity
struct WalletEntry {
    uint64  registeredAt;       // Block timestamp of registration
    uint64  incidentTimestamp;  // Unix timestamp of incident (0 if unknown)
    uint64  batchId;            // Operator batch ID (0 for individual/cross-chain)
    uint8   bridgeId;           // 0 = local, 1 = Hyperlane
    bool    isSponsored;        // True if someone else paid gas
}
```

The struct is 26 bytes, fitting in a single EVM storage slot (6 bytes spare). This is a deliberate design choice: storage carries minimal data per entry, while events carry rich provenance data (chain IDs, message IDs, reporters, etc.).

Fields that were moved to events-only:

| Field             | Why events-only                                                                                          |
| ----------------- | -------------------------------------------------------------------------------------------------------- |
| `reportedChainId` | Emitted in `WalletRegistered` -- needed for indexing/display but not for on-chain `isRegistered` lookups |
| `sourceChainId`   | Emitted in `CrossChainWalletRegistered` -- only relevant for cross-chain provenance tracing              |
| `messageId`       | Emitted in `CrossChainWalletRegistered` -- only relevant for bridge explorer linking                     |

The storage key already encodes identity (wallet address + chain namespace). Events encode provenance (where, when, how). The indexer reconstructs the full picture by joining both.

## Two-Phase Registration

Every individual wallet registration goes through two phases separated by a randomized grace period. This prevents single-transaction phishing -- an attacker cannot trick a user into registering a legitimate wallet in one step.

### What Actually Prevents Phishing

The primary anti-phishing control is **not** the randomized delay. It is the `windowBlockHash`
commitment in the registration signature: the signature must commit to the hash of a block at or
after `gracePeriodStart`. That block -- and therefore its hash -- did not exist when the
acknowledgement was signed, so the registration signature **cannot** have been produced in the
same sitting as the acknowledgement.

Without it, a phishing page could collect both signatures seconds apart and submit the second one
itself once the delay had quietly elapsed. The randomization is defense in depth: it widens the
timing window an attacker must cover, but nothing depends on `block.prevrandao` being
unpredictable (it is proposer-influenceable and is not cryptographically secure).

### Phase 1: Acknowledge

```solidity
function acknowledge(
    address registeree,        // Wallet being registered
    address trustedForwarder,  // Who can call register() (can be same address)
    uint64  reportedChainId,   // Chain where incident occurred
    uint64  incidentTimestamp,  // When it happened (0 if unknown)
    uint256 deadline,          // EIP-712 signature expiry (timestamp)
    uint256 nonce,             // Replay protection
    uint8 v, bytes32 r, bytes32 s
) external;
```

- Requires `msg.sender == trustedForwarder` (reverts with `WalletRegistry__InvalidForwarder`)
- Validates the signature deadline is in the future and no more than 2 hours out
  (`TimingConfig.MAX_SIGNATURE_LIFETIME`) -- reverts with `WalletRegistry__DeadlineExpired` or
  `WalletRegistry__DeadlineTooFarInFuture`
- Rejects a future-dated `incidentTimestamp` with `WalletRegistry__InvalidIncidentTimestamp`
  (`0` is the accepted "unknown" sentinel and is still allowed)
- Checks wallet is not already registered or pending
- Validates nonce matches `nonces[registeree]` (reverts with `WalletRegistry__InvalidNonce` on mismatch)
- Verifies EIP-712 signature from `registeree`
- Increments nonce
- Stores `AcknowledgementData` with randomized grace period timing
- Emits `WalletAcknowledged(registeree, trustedForwarder, isSponsored)`

**Only the forwarder named in the signature may open the window.** All three registration methods
already satisfy this -- standard: the registeree itself; self-relay: the gas wallet; P2P relay: the
relayer. Requiring it closes two holes: an unrelated third party could otherwise grind their own
address to steer the "randomized" timing, and could burn a victim's nonce to grief them. Phase 2
already demanded `msg.sender == trustedForwarder`; this makes both phases consistent.

### Phase 2: Register

```solidity
function register(
    address registeree,
    address trustedForwarder,  // Must match ack phase AND msg.sender
    uint64  reportedChainId,   // Must match ack phase
    uint64  incidentTimestamp,  // Must match ack phase
    uint256 deadline,
    uint256 nonce,
    uint256 windowBlock,       // Block whose hash the signature commits to
    uint8 v, bytes32 r, bytes32 s
) external payable;
```

- **Only** `trustedForwarder` can call this (`msg.sender` must match)
- Grace period must have elapsed (`block.number >= gracePeriodStart`)
- Must be within deadline window (`block.number < deadline`)
- `reportedChainId` and `incidentTimestamp` must match the acknowledge phase
- Validates nonce matches `nonces[registeree]` (fail-fast, before signature verification)
- Resolves `windowBlockHash = blockhash(windowBlock)` -- see below
- Verifies second EIP-712 signature from `registeree` (the signed struct includes `windowBlockHash`)
- Reverts with `WalletRegistry__AlreadyRegistered` if a cross-chain or operator path registered the
  wallet during the grace period
- Stores `WalletEntry` permanently, deletes pending acknowledgement
- Collects fee (if a FeeManager is configured; in free mode the full `msg.value` is refunded)
- Emits `WalletRegistered(identifier, reportedChainId, incidentTimestamp, isSponsored)`

#### The windowBlock Commitment

`windowBlock` is **not** part of the signed struct -- the signed `windowBlockHash` binds it, so a
false value simply fails the `blockhash` comparison. It must satisfy:

| Bound                              | Error                                        |
| ---------------------------------- | -------------------------------------------- |
| `windowBlock >= gracePeriodStart`  | `TimingConfig__WindowBlockBeforeGracePeriod` |
| `windowBlock < block.number`       | `TimingConfig__WindowBlockNotMined`          |
| `block.number - windowBlock < 256` | `TimingConfig__WindowBlockTooOld`            |

The 256-block bound is the EVM's `blockhash` availability horizon. A registration signature
therefore **ages out**: if the forwarder waits too long between signing and submitting, the
transaction reverts and the user must sign again against a fresher `windowBlock`.

### Dual Deadline System

Two different deadlines are in play:

| Deadline                       | Unit                          | Purpose                                               |
| ------------------------------ | ----------------------------- | ----------------------------------------------------- |
| `deadline` param               | Timestamp (`block.timestamp`) | EIP-712 signature expiry -- prevents stale signatures |
| `AcknowledgementData.deadline` | Block number (`block.number`) | Grace period window -- enforces registration timing   |

### Grace Period Timing

Grace and deadline are configured as **block counts** per chain, then randomized: the actual grace
period lands in `[graceBlocks, 2 * graceBlocks)` blocks.

| Chain         | `block.number` ticks at | Grace blocks | Deadline blocks | Actual grace period |
| ------------- | ----------------------- | ------------ | --------------- | ------------------- |
| Base/Optimism | 2s                      | 60           | 300             | ~2-4 min            |
| Ethereum L1   | 12s                     | 10           | 50              | ~2-4 min            |
| Arbitrum      | ~12s (L1 blocks!)       | 10           | 50              | ~2-4 min            |
| Anvil (local) | 13s                     | 2            | 50              | ~26-52s             |

:::warning
On Arbitrum, `block.number` inside a contract returns the **L1** block number, which advances at
~12s -- not the ~0.25s L2 rate. Arbitrum therefore uses the same block counts as Ethereum L1.
:::

The constructor enforces `deadlineBlocks >= 2 * graceBlocks + 1`, which guarantees that every
randomized draw leaves at least one block on which `register` can actually succeed.

## Three Registration Methods

| Method         | Who signs  | Who pays (`trustedForwarder`) | `isSponsored` |
| -------------- | ---------- | ----------------------------- | ------------- |
| **Standard**   | registeree | registeree (same address)     | `false`       |
| **Self-Relay** | registeree | Different wallet              | `true`        |
| **P2P Relay**  | registeree | Helper (via libp2p)           | `true`        |

`isSponsored` is derived as `registeree != trustedForwarder`. The contract does not distinguish between self-relay and P2P relay -- both are "sponsored" registrations where someone else pays gas.

## Other Registration Paths

### Cross-Chain (Hub Only)

```solidity
function registerFromHub(
    bytes32 namespaceHash,
    bytes32 chainRefHash,
    bytes32 identifier,       // address as bytes32
    bytes32 reportedChainId,
    uint64  incidentTimestamp,
    bytes32 sourceChainId,
    bool    isSponsored,
    uint8   bridgeId,         // 1 = Hyperlane
    bytes32 messageId
) external onlyHub;
```

Called by `FraudRegistryHub` when a cross-chain message arrives from a `SpokeRegistry`. The entry struct stores only `registeredAt`, `incidentTimestamp`, `bridgeId`, and `isSponsored`. Cross-chain provenance fields (`reportedChainId`, `sourceChainId`, `messageId`) are emitted in events only -- they are not written to storage.

Emits both `WalletRegistered` and `CrossChainWalletRegistered`.

**This path never reverts.** Hyperlane re-delivers a reverting message indefinitely, so a single
malformed payload would become permanently undeliverable. Instead, inputs that every other path
rejects are absorbed:

| Input                            | Behavior                                       |
| -------------------------------- | ---------------------------------------------- |
| `identifier == bytes32(0)`       | Returns immediately (message marked delivered) |
| Wallet already registered        | Returns immediately, no events                 |
| Future-dated `incidentTimestamp` | Clamped to `0` (the "unknown" sentinel)        |

### Operator Batch

```solidity
function registerWalletsFromOperator(
    bytes32   operatorId,
    bytes32[] identifiers,        // Wallet addresses as bytes32
    bytes32[] reportedChainIds,
    uint64[]  incidentTimestamps
) external onlyOperatorSubmitter returns (uint256 batchId);
```

Bypasses two-phase flow entirely. Returns the batch ID.

Per-entry, it **skips** (without reverting) zero identifiers and wallets that are already
registered. The batch as a whole still reverts on:

| Condition                                   | Error                                      |
| ------------------------------------------- | ------------------------------------------ |
| Empty array                                 | `WalletRegistry__EmptyBatch`               |
| More than `MAX_BATCH_SIZE` (10,000) entries | `WalletRegistry__BatchTooLarge`            |
| Arrays of differing length                  | `WalletRegistry__ArrayLengthMismatch`      |
| Any future-dated `incidentTimestamps[i]`    | `WalletRegistry__InvalidIncidentTimestamp` |
| Every entry skipped (actual count 0)        | `WalletRegistry__EmptyBatch`               |

A future-dated incident rejects the **whole batch** rather than skipping the entry: it is a fixable
mistake in the operator's input file, and silently dropping entries would leave the operator
believing data landed when it did not. Likewise, a batch in which nothing was actually registered
reverts rather than burning a batch ID and materializing a phantom zero-entry batch in the indexer.

Emits `WalletRegistered` per entry, then `BatchCreated` with the actual count (excluding skipped entries).

## Nonce Tracking

```solidity
mapping(address => uint256) public nonces;
```

Per-address, incremented on each successful `acknowledge()` and `register()` call. Used for EIP-712 replay protection. The nonce must be provided as a parameter and match the on-chain value -- mismatches revert with `WalletRegistry__InvalidNonce` before signature verification (fail-fast).

## Events

| Event                        | When                             | Key fields                                                                    |
| ---------------------------- | -------------------------------- | ----------------------------------------------------------------------------- |
| `WalletAcknowledged`         | Phase 1 complete                 | `registeree`, `trustedForwarder`, `isSponsored`                               |
| `WalletRegistered`           | Phase 2 / cross-chain / operator | `identifier` (bytes32), `reportedChainId`, `incidentTimestamp`, `isSponsored` |
| `CrossChainWalletRegistered` | Cross-chain only                 | `identifier`, `sourceChainId`, `bridgeId`, `messageId`                        |
| `BatchCreated`               | Operator batch                   | `batchId`, `operatorId`, `walletCount`                                        |

The `identifier` in `WalletRegistered` is `bytes32(uint256(uint160(address)))`. To recover the address: `address(uint160(uint256(identifier)))`.

## View Functions

| Function                             | Returns                                                                                           |
| ------------------------------------ | ------------------------------------------------------------------------------------------------- |
| `isWalletRegistered(string caip10)`  | Whether wallet is registered (CAIP-10 string interface)                                           |
| `isWalletRegistered(address wallet)` | Whether wallet is registered (gas-efficient EVM overload)                                         |
| `getWalletEntry(...)`                | Full `WalletEntry` struct (both overloads)                                                        |
| `isWalletPending(address)`           | Whether wallet has active acknowledgement                                                         |
| `getAcknowledgementData(address)`    | Full `AcknowledgementData` struct for a pending registration                                      |
| `getDeadlines(address)`              | `(currentBlock, expiryBlock, startBlock, graceStartsAt, timeLeft, isExpired)`                     |
| `getSignatureDeadline(...)`          | Signing deadline (timestamp) for frontend signature generation                                    |
| `nonces(address)`                    | Current nonce for replay protection                                                               |
| `getBatch(uint256 batchId)`          | Operator batch metadata                                                                           |
| `batchCount()`                       | Total number of operator batches created                                                          |
| `quoteRegistration(address)`         | Total fee in wei (0 when no FeeManager is configured)                                             |
| `quoteFeeBreakdown(address)`         | `FeeBreakdown` -- bridge fee, registration fee, total, bridge name (bridge fields 0/empty on hub) |

:::info
`getSignatureDeadline` returns **only** the deadline -- there is deliberately no hash-struct return
value. The registration typehash includes `windowBlockHash`, which is not knowable at the time this
is called: the frontend fetches the deadline _before_ signing and resolves the window block later,
at signing time. Callers build their own typed data (see `packages/signatures`).
:::
