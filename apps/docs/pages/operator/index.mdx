# Operator Protocol

Operators are the backbone of the registry's credibility. Without them, SWR is limited to self-attestation - individuals reporting their own wallets as stolen. With operators, it becomes an **industry-wide fraud intelligence database**.

## What Is an Operator?

An operator is a DAO-approved entity with bulk fraud intelligence:

- **Exchanges** - Coinbase, Kraken, Binance detect compromised accounts daily through internal monitoring
- **Security firms** - Chainalysis, TRM Labs, Elliptic track stolen funds across chains
- **Community investigators** - ZachXBT and similar on-chain sleuths with verified track records

The DAO votes to approve operators, granting them permission to batch-submit fraud data directly to the registry - no two-phase signature flow required.

## Why Operators Matter

Individual self-attestation is important for victims. But the registry becomes a **standard** when institutional operators are contributing fraud data.

The model: operators accumulate fraud intelligence through their internal systems, then periodically batch-submit entries to SWR — weekly, monthly, or at whatever cadence fits their operations. A single batch can contain hundreds or thousands of entries across wallets, transactions, and contracts.

1. An exchange flags compromised wallets through internal fraud monitoring over weeks or months
2. They batch-submit the accumulated entries to SWR on their own schedule
3. Every other exchange, wallet, and off-ramp can query the registry for shared fraud intelligence

This isn't a real-time firehose — it's a shared ledger that operators contribute to at their own pace, and everyone benefits from the aggregate data.

## OperatorRegistry Contract

The `OperatorRegistry` contract is a DAO-controlled whitelist. It stores approved operators and their permissions.

```solidity
struct Operator {
    bool approved;        // Is operator currently approved
    uint8 capabilities;   // Bitmask: 0x01=wallet, 0x02=tx, 0x04=contract
    uint64 approvedAt;    // Block number when approved
    uint64 revokedAt;     // Block number when revoked (0 if active)
    string identifier;    // Human-readable name (e.g., "Coinbase", "ZachXBT")
}
```

Operators are scoped to specific registries via a **capabilities bitmask**. An exchange might only need wallet and transaction access, while a contract auditing firm might only need contract registry access.

### Capabilities Bitmask

| Value  | Constant            | Registry            | Example Use                                    |
| ------ | ------------------- | ------------------- | ---------------------------------------------- |
| `0x01` | `WALLET_REGISTRY`   | Stolen Wallet       | Exchange reporting compromised user accounts   |
| `0x02` | `TX_REGISTRY`       | Stolen Transaction  | Tracing firms flagging fraudulent transactions |
| `0x04` | `CONTRACT_REGISTRY` | Fraudulent Contract | Security firms cataloging phishing contracts   |
| `0x07` | `ALL_REGISTRIES`    | All three           | Full-spectrum fraud intelligence providers     |

`0x07` is the union of all three bits, not a bit of its own.

Capabilities are defined in the `RegistryCapabilities` library - a single source of truth shared across all registry contracts:

```solidity
library RegistryCapabilities {
    uint8 internal constant WALLET_REGISTRY   = 0x01;
    uint8 internal constant TX_REGISTRY       = 0x02;
    uint8 internal constant CONTRACT_REGISTRY = 0x04;
    uint8 internal constant ALL_REGISTRIES    = 0x07;
}
```

## Key Functions

### Write Functions (DAO Only)

All write functions are restricted to `onlyOwner`. The contract owner is the **SWR DAO** (a multisig or governance contract). Only the DAO can approve, revoke, or update operators — operators themselves cannot modify the registry's whitelist.

```solidity
// Approve a new operator with specified capabilities
// Setup-only — see Timelocked Governance below
function approveOperator(
    address operator,
    uint8 capabilities,
    string calldata identifier
) external onlyOwner onlyDuringSetup;

// Revoke an operator (immediate, always)
function revokeOperator(address operator) external onlyOwner;

// Change an operator's capabilities
// Reductions immediate; escalations must take the timelocked path
function updateCapabilities(
    address operator,
    uint8 capabilities
) external onlyOwner;
```

## Timelocked Governance

`OperatorRegistry` inherits `TimelockOwnable`. It has two lifecycle phases:

**During setup** (before `completeSetup()`), the immediate setters above work as written — this is deployment and initial wiring.

**After `completeSetup()`**, granting trust takes a two-step path with a mandatory delay:

```solidity
// 1. Propose — emits ActionProposed(actionKey, activationTime)
function proposeOperator(address operator, uint8 capabilities, string calldata identifier) external onlyOwner;

// 2. Wait ACTIVATION_DELAY (2 days), then activate within ACTIVATION_EXPIRY (14 days)
function activateOperator(address operator, uint8 capabilities, string calldata identifier) external onlyOwner;

// Same pair for capability escalation
function proposeCapabilities(address operator, uint8 capabilities) external onlyOwner;
function activateCapabilities(address operator, uint8 capabilities) external onlyOwner;
```

Calling `approveOperator` after setup reverts with `TimelockOwnable__UseTimelockedPath()`. The arguments to `activate*` must match the proposal exactly — the action key is a hash of the function name and every parameter.

| Action                                      | Post-setup path                                         |
| ------------------------------------------- | ------------------------------------------------------- |
| Approve a new operator                      | `proposeOperator` → 2 days → `activateOperator`         |
| **Escalate** capabilities (grant a new bit) | `proposeCapabilities` → 2 days → `activateCapabilities` |
| **Reduce** capabilities (drop a bit)        | `updateCapabilities` — immediate                        |
| Revoke an operator                          | `revokeOperator` — immediate                            |

### Why escalation is timelocked but reduction isn't

Anything that only **removes** access is an emergency lever and stays instant. Anything that **grants** access waits.

Without that asymmetry the delay on `approveOperator` would be fully bypassable: approve an operator with a benign capability through the timelocked path, then escalate to `ALL_REGISTRIES` in a single transaction. That would hand out instant access to `ContractRegistry.registerContractsFromOperator` — which is operator-only precisely because it has no two-phase EIP-712 protection.

`updateCapabilities` therefore checks whether the new mask sets any bit the operator does not already hold, and reverts `TimelockOwnable__UseTimelockedPath()` on escalation once setup is complete.

`activateCapabilities` also re-checks approval at activation time: an operator revoked during the 2-day window cannot have capabilities silently restored, which would otherwise defeat the revoke.

### View Functions

```solidity
// Check if address is an approved operator
function isApproved(address operator) external view returns (bool);

// Check if operator is approved for a specific registry type
function isApprovedFor(address operator, uint8 registryType) external view returns (bool);

// Get full operator data
function getOperator(address operator) external view returns (Operator memory);

// Get an operator's raw capabilities bitmask
function getCapabilities(address operator) external view returns (uint8);

// Get total count of approved operators
function approvedOperatorCount() external view returns (uint256);
```

### Events

```solidity
event OperatorApproved(address indexed operator, uint8 capabilities, string identifier, uint64 approvedAt);
event OperatorRevoked(address indexed operator, uint64 revokedAt);
event OperatorCapabilitiesUpdated(address indexed operator, uint8 oldCapabilities, uint8 newCapabilities);
```

## Hub-Only

Operators exist **only on the hub chain** (Base). There are no operator submissions from spoke chains.

Cross-chain registrations from individuals go through spoke chains via Hyperlane, but operator batch submissions are always direct to the hub. This simplifies permission management - the DAO only needs to maintain one whitelist.

## No Two-Phase for Operators

Individual registrations require a [two-phase EIP-712 flow](/concepts/two-phase-registration) to prevent phishing. Operators skip this entirely.

The DAO approval process **is** the trust mechanism. An entity approved by governance vote has already passed the bar that two-phase registration provides for individuals. Adding a grace period to operator batch submissions would slow down bulk intelligence sharing for no security benefit.

## Error Conditions

| Error                                     | When                                            |
| ----------------------------------------- | ----------------------------------------------- |
| `OperatorRegistry__ZeroAddress()`         | Operator address is `address(0)`                |
| `OperatorRegistry__AlreadyApproved()`     | Operator is already approved                    |
| `OperatorRegistry__NotApproved()`         | Trying to revoke/update a non-approved operator |
| `OperatorRegistry__InvalidCapabilities()` | Capabilities is `0` or exceeds `ALL_REGISTRIES` |

An operator that lacks the required capability bit is not rejected here — `isApprovedFor` simply returns `false` and the caller reverts. For batch submissions that surfaces as `OperatorSubmitter__NotApprovedOperator()`.

Inherited from `TimelockOwnable`:

| Error                                     | When                                                                       |
| ----------------------------------------- | -------------------------------------------------------------------------- |
| `TimelockOwnable__UseTimelockedPath()`    | Immediate setter (or capability escalation) called after `completeSetup()` |
| `TimelockOwnable__NotProposed()`          | Activating an action that was never proposed, or whose arguments differ    |
| `TimelockOwnable__TooEarly()`             | Activating before the 2-day `ACTIVATION_DELAY` has elapsed                 |
| `TimelockOwnable__Expired()`              | Activating after the 14-day `ACTIVATION_EXPIRY` window closed — re-propose |
| `TimelockOwnable__AlreadyPending()`       | Proposing an action that already has a live pending proposal               |
| `TimelockOwnable__SetupNotComplete()`     | Proposing before `completeSetup()` — the immediate setters are still open  |
| `TimelockOwnable__SetupAlreadyComplete()` | Calling `completeSetup()` twice                                            |
| `TimelockOwnable__RenounceDisabled()`     | Attempting to renounce ownership after setup                               |
