# Indexer & Search

On-chain storage gives you O(1) lookups for a single identifier (`isWalletRegistered(address)`). But listing, filtering, sorting, and aggregate statistics require an indexer. The SWR indexer powers the dashboard and search UI.

## Technology

- **[Ponder](https://ponder.sh)** 0.16.x -- Event-driven blockchain indexer
- **PostgreSQL** (production) / PGlite (development)
- **Auto-generated GraphQL API** -- Query any indexed table with filters, pagination, and sorting

## What Gets Indexed

| ------------------------------ | --------------------------------- | ----------------------------------------------------------------- |
| `WalletAcknowledged`           | `walletAcknowledgement`           | registeree, trustedForwarder, isSponsored, status                 |
| `WalletRegistered`             | `stolenWallet`                    | walletAddress, caip10, registeredAt, isSponsored, reportedChainId |
| `BatchCreated`                 | `walletBatch`                     | batchId, operatorId, walletCount, operator                        |
| `TransactionBatchAcknowledged` | `transactionBatchAcknowledgement` | reporter, trustedForwarder, dataHash, status                      |
| `TransactionRegistered`        | `transactionInBatch`              | txHash, chainIdHash, caip2ChainId, reporter                       |
| `TransactionBatchRegistered`   | `transactionBatch`                | batchId, dataHash, transactionCount, isSponsored                  |
| `TransactionBatchCreated`      | `transactionBatch`                | batchId, operatorId, transactionCount (operator path)             |
| `ContractRegistered`           | `fraudulentContract`              | contractAddress, caip2ChainId, batchId, operator                  |
| `ContractBatchCreated`         | `fraudulentContractBatch`         | batchId, operatorId, contractCount                                |
| `CrossChainWalletRegistered`   | `crossChainMessage`               | messageId, sourceChainId, bridgeId, status                        |
| `WalletRegistrationReceived`   | `crossChainMessage`               | messageId, wallet, sourceChainId                                  |
| `TransactionBatchReceived`     | `crossChainMessage`               | messageId, dataHash, sourceChainId                                |
| `OperatorApproved`             | `operator`                        | identifier, capabilities, approved                                |
| `OperatorRevoked`              | `operator`                        | approved=false, revokedAt                                         |
| `OperatorCapabilitiesUpdated`  | `operatorCapabilityChange`        | oldCapabilities, newCapabilities                                  |
| `WalletSoulboundMinted`        | `walletSoulboundToken`            | wallet, minter, tokenId                                           |
| `SupportSoulboundMinted`       | `supportSoulboundToken`           | supporter, amount, tokenId                                        |

A `registryStats` table tracks global aggregates, updated incrementally on every event.

:::info
**No grace-period window is indexed.** `walletAcknowledgement` deliberately has no
`gracePeriodStart` / `gracePeriodEnd` columns and no `expired` status. The contract derives the
window from `TimingConfig` with a per-acknowledgement random component and does **not** put the
result on `WalletAcknowledged`, so the indexer cannot know it — the columns that used to exist
served fabricated `block.number + 5 / + 20` constants to clients. Expiry is a function of the
current block, so evaluate it against the contract (`deadlines.isExpired`), never against the
indexer.

Acknowledgement `status` is `pending | registered | superseded`. `registered` means this
acknowledgement completed its own two-phase flow. `superseded` means the wallet ended up
registered by another route (usually an operator batch) while the ack was still pending — the
registration is real, but the registeree never signed the second message.
:::

### Search Type Detection

The frontend determines the query type by format:

- **Address** (42 chars, `0x` prefix) -- Searches both wallet and contract registries in parallel
- **Transaction hash** (66 chars, `0x` prefix) -- Searches the transaction registry
- **CAIP-10** (contains `:` separator, e.g., `eip155:8453:0x...`) -- Searches **both** registries, same as the bare-address path (`searchAddressByCAIP10`)
- **ENS name** (ends with `.eth`) -- Resolves to address first, then searches as address
- **Unsupported** -- A well-formed identifier in a namespace this registry cannot answer for. **Throws**, see below.

### Fail-Closed Contract (read this before integrating)

`@swr/search` **throws rather than returning a result that reads as "clean."** A negative answer
is only ever returned when it is a real negative.

```ts
import { search, SearchUnavailableError, isSearchUnavailableError } from '@swr/search';

try {
  const result = await search(config, query);
  if (isCompromised(result)) block();
  else allow();
} catch (err) {
  if (isSearchUnavailableError(err)) {
    // We do NOT know whether this address is clean. Do not allow on this path.
    hold(err.unverified); // which registries could not be reached
  }
  throw err;
}
```

`SearchUnavailableError` carries `unverified` (the registries that could not be consulted) and
`reason`:

| `reason`                   | Meaning                                                                     |
| -------------------------- | --------------------------------------------------------------------------- |
| `'unreachable'`            | The query was sent and failed — indexer down, network error                 |
| `'unsupported-identifier'` | The registry has no form for this identifier, so there was nothing to query |

It is thrown **only when nothing was found**. A search that gets a hit returns normally, with any
unreachable registries listed in the result's `unverified` field — a positive result is still
actionable even if coverage was partial.

:::danger
The reason this is an exception rather than `{ found: false }`: an integrator writing the obvious
`if (!isCompromised(r)) allow()` would otherwise clear a withdrawal for an address that nothing
had actually looked at. `getResultStatus()` would report `not-found` and `isCompromised()` would
report `false` for a query that never reached a registry.
:::

A stale indexer has the same shape of hazard — it answers "not found" for everything it has not
reached yet. Consumers acting on a clean result should check the lag:

```ts
import { getIndexerStatus, isIndexerStale, DEFAULT_MAX_LAG_SECONDS } from '@swr/search';
```

The one safe negative-without-a-query is `type: 'invalid'`: the input is not an identifier at
all, so there is no registry entry it could be missing.

### Batch Detail Queries

Batch detail uses a two-step fetch pattern for efficiency:

1. **Step 1**: Fetch the batch summary by `batchId`
2. **Step 2**: Fetch entries by `transactionHash` (the join key)

| Query                                                                   | Purpose                              |
| ----------------------------------------------------------------------- | ------------------------------------ |
| `WALLET_BATCH_ONLY_QUERY` + `WALLET_ENTRIES_BY_TX_HASH_QUERY`           | Wallet batch detail                  |
| `TRANSACTION_BATCH_ONLY_QUERY` + `TRANSACTION_ENTRIES_BY_TX_HASH_QUERY` | Transaction batch detail             |
| `CONTRACT_BATCH_DETAIL_QUERY`                                           | Contract batch detail (single query) |

## Batch-Entry Linking

Per-entry events (`WalletRegistered`, `TransactionRegistered`) do not carry a `batchId` field. This is a deliberate gas optimization -- adding an indexed `batchId` to every per-entry event would cost extra gas per entry, and batches can contain hundreds of entries.

Instead, the indexer joins entries to their parent batch using `transactionHash`. All per-entry events and the batch summary event fire in the same transaction, so they share the same hash.

:::info
The entry structs stored on-chain are minimal (1 storage slot each) and do not contain provenance fields like `reportedChainId`, `sourceChainId`, `messageId`, or `reporter`. The indexer reads these fields from **events**, not from entry struct storage. This means the indexer is the authoritative source for rich query data -- on-chain `getWalletEntry()` / `getTransactionEntry()` / `getContractEntry()` return only the minimal struct fields needed for on-chain lookups.
:::

```
Same transaction:
  ├── WalletRegistered(identifier_1, ...)     ← no batchId
  ├── WalletRegistered(identifier_2, ...)     ← no batchId
  ├── WalletRegistered(identifier_3, ...)     ← no batchId
  └── BatchCreated(batchId, operatorId, 3)    ← has batchId
                                                 ↑ same transactionHash
```

The `ContractRegistered` event is the exception -- it does include `batchId` on per-entry events since contract registrations are operator-only (no individual path).

## Cross-Chain Message Tracking

The `crossChainMessage` table correlates spoke-to-hub message flow. There are exactly **two**
statuses:

```
Status: received | registered
```

The registry event comes **first**. `CrossChainInbox` emits `WalletRegistrationReceived` /
`TransactionBatchReceived` only _after_ it has delegated to the registries, so the
`CrossChainWalletRegistered` / `CrossChainTransactionRegistered` handler runs first and creates
the row already at `registered`. The inbox handler then runs and fills in what only it knows —
without ever downgrading a `registered` row back to `received`, which would make a completed
message look stuck.

Both handlers insert-or-update rather than find-then-update, since either may be the one that
sees the message first.

:::warning
**`sourceChainId` may hold a Hyperlane domain, not a chain ID.** The inbox handler only receives
the Hyperlane `origin` domain; when `@swr/chains` cannot map it to a chain, the raw domain is
kept (a domain is still a usable correlation key) rather than writing `0`. The two are different
numbering spaces. Check the `sourceChainIsDomain` flag before rendering this as a chain ID or
joining against one.

`sourceChainCAIP2` is never ambiguous — it is only written when the chain actually resolved, and
is `null` otherwise. Prefer it.
:::

Cross-chain provenance is mirrored onto the entity tables: `stolenWallet` and `transactionBatch`
both carry `sourceChainId`, `sourceChainCAIP2`, `bridgeId` and `messageId`. All four are `NULL`
for a locally-registered row, which is how "was this delivered from a spoke?" is answered.
`TransactionBatchRegistered` carries none of this itself, so the batch handler reads it back off
the `crossChainMessage` row keyed by `hubTxHash`.

## Environment Configuration

| Environment | Chain        | Chain ID | Database            | RPC                     |
| ----------- | ------------ | -------- | ------------------- | ----------------------- |
| Development | Local Anvil  | 31337    | PGlite (in-process) | `http://localhost:8545` |
| Staging     | Base Sepolia | 84532    | PostgreSQL          | Alchemy / public RPC    |
| Production  | Base         | 8453     | PostgreSQL          | Alchemy                 |

The GraphQL API listens on **port 42069** (`http://localhost:42069` in development — the default
`VITE_INDEXER_URL` for the web app).

Key environment variables:

| Variable               | Purpose                                                                         |
| ---------------------- | ------------------------------------------------------------------------------- |
| `PONDER_ENV`           | `development`, `staging`, or `production`                                       |
| `PONDER_RPC_URL_*`     | Chain-specific RPC endpoints (**required** for staging/production)              |
| `PONDER_START_BLOCK_*` | Contract deployment block — **throws** if unset for staging/production          |
| `DATABASE_URL`         | PostgreSQL connection string — optional in dev, required for staging/production |
| `DATABASE_SCHEMA`      | Schema name for tooling that reads it directly                                  |

In development, Ponder uses PGlite (an embedded PostgreSQL) when `DATABASE_URL` is unset, so no
external database is needed. Set `DATABASE_URL` only to run against a real Postgres.

`ponder.config.ts` fails fast rather than misbehaving quietly: for staging and production it
throws if the RPC URL is missing, if hub contracts are unconfigured in `@swr/chains`, or if the
start block is `<= 0` — syncing a live chain from block 0 would be extremely slow and costly.

The run scripts pin the schema on the command line: `ponder dev --schema swr_dev` for
development, `ponder start --schema swr_prod` for production.

## CAIP-2 Resolution

The indexer resolves `bytes32` chain ID hashes to human-readable CAIP-2 strings (e.g., `eip155:8453`) using `@swr/chains` utilities:

```typescript
import { resolveChainIdHash, caip2ToNumericChainId } from '@swr/chains';

// bytes32 → "eip155:8453"
const caip2 = resolveChainIdHash(reportedChainId);

// "eip155:8453" → 8453
const numeric = caip2ToNumericChainId(caip2);
```

This resolution happens at indexing time, so GraphQL consumers get readable chain identifiers without needing to decode hashes themselves.
