# Testnet Deployment

Deploy the full SWR stack to Base Sepolia (hub) and Optimism Sepolia (spoke).

## Overview

Two pnpm commands deploy everything:

```bash
cd packages/contracts
pnpm deploy:testnet:hub    # All hub contracts to Base Sepolia
pnpm deploy:testnet:spoke  # Spoke contracts to Optimism Sepolia
```

After deployment, configure trust relationships via `cast send`, finalize setup mode on **both**
chains (Step 5 — the spoke finalize is easy to miss and leaves the adapter allowlist
unprotected if skipped), and fill in addresses in `@swr/chains`.

### Run the forked Hyperlane check first

**A green `forge test` does not prove the bridge works.** Every Hyperlane test in the suite
except one runs against `test/mocks/MockMailbox.sol`, and a mock only proves our code agrees
with our own idea of the interface. That is not a theoretical gap: the adapter originally
shipped built against the Hyperlane **v2** `IMailbox` (non-payable `dispatch`, no
`quoteDispatch`) while every live Base/Optimism mailbox is **v3**, and the suite stayed green
throughout — because MockMailbox had the same wrong shape as the adapter.

`test/HyperlaneForked.t.sol` is the only test that breaks that circle, and it skips itself
unless an RPC is supplied. Run it before you deploy:

```bash
cd packages/contracts
OPTIMISM_SEPOLIA_RPC=https://<your-op-sepolia-rpc> \
  forge test --match-contract HyperlaneForked -vv
```

Expect `4 passed; 0 failed; 0 skipped`. **If you see `0 passed` or any `[SKIP]`, the check did
not run** — the env var is missing or misspelled, and you have verified nothing. Do not proceed
on a skipped result.

Re-run it after any change to the vendored interfaces in `src/vendor/hyperlane/`. There is a CI
equivalent (`.github/workflows/hyperlane-forked.yml`, **Actions → Hyperlane forked integration →
Run workflow**), but it is manual only and needs an `OPTIMISM_SEPOLIA_RPC` repository secret.
Nothing runs it automatically, so treat the local command above as the deployment gate.

## Step 1: Environment Setup

Copy the example file — it is the source of truth for this deployment, and every key in it is
a name the deploy scripts actually read:

```bash
cd packages/contracts
cp .env.testnet.example .env.testnet   # .env.testnet is gitignored
```

To get through Step 2 you only need the inputs at the top:

```bash
PRIVATE_KEY=0x...                       # dedicated testnet wallet, never your mainnet key
BASE_SEPOLIA_RPC=https://base-sepolia.g.alchemy.com/v2/YOUR_KEY
OPTIMISM_SEPOLIA_RPC=https://sepolia.optimism.io
BASESCAN_API_KEY=...
OPTIMISM_ETHERSCAN_API_KEY=...

# Hyperlane infrastructure (official deployed addresses — don't change these)
HUB_HYPERLANE_MAILBOX=0x6966b0E55883d49BFB24539356a2f8A673E02039
SPOKE_HYPERLANE_MAILBOX=0x6966b0E55883d49BFB24539356a2f8A673E02039

HUB_CHAIN_ID=84532                      # Hyperlane domain of the hub chain
```

The rest of the file is **outputs you paste back in** after each deploy — every hub and spoke
address, plus `DAO_OWNER` for the handover. They are not optional extras: `finalizeSetup` /
`finalizeSpokeSetup` look each contract up by its exact env key and **silently skip anything
unset**, while `verifySetup` / `verifySpokeSetup` then **reject** the same unset target. A
missing or misnamed variable therefore gives you a finalize run that looks clean and a verify
run that fails — or a contract shipped with its immediate setters still open.

:::info
To exclude a contract you genuinely did not deploy, opt out by name so the exclusion is a
recorded decision rather than an oversight:

```bash
SKIP_SPOKE_FEE_MANAGER=true
SKIP_SPOKE_SOULBOUND_FORWARDER=true
```

`verifySetup` / `verifySpokeSetup` reject an unset target precisely because a forgotten
variable is indistinguishable from a contract that was never locked.
:::

Read `.env.testnet.example` in full before deploying — it documents each key's role, which
script reads it, and the run order.

## Step 2: Deploy Hub (Base Sepolia)

This deploys everything to the hub chain in one shot: core registries, FeeManager (with real Chainlink ETH/USD feed), operator infrastructure, cross-chain inbox, and all soulbound contracts.

```bash
cd packages/contracts
pnpm deploy:testnet:hub
```

:::info
First time? Do a dry run to check everything works:

```bash
source .env.testnet
forge script script/Deploy.s.sol:Deploy \
  --sig "deployHub()" \
  --rpc-url $BASE_SEPOLIA_RPC -vvvv
```

:::

The output will print all deployed addresses. **Paste every one of them into the HUB ADDRESSES
section of `.env.testnet`** — `verifySetup` requires all of them (see Step 1). The two you need
immediately for Step 3 are:

- **CrossChainInbox** address (for `HUB_INBOX_ADDRESS`)
- **SoulboundReceiver** address (for `SOULBOUND_RECEIVER`)
- **HyperlaneAdapter** address won't appear here (that's on the spoke)

## Step 3: Deploy Spoke (Optimism Sepolia)

Add hub addresses to `.env.testnet` from the Step 2 output:

```bash
# Convert the CrossChainInbox address to a LEFT-padded bytes32:
#   cast to-uint256 0x<CROSS_CHAIN_INBOX_ADDRESS>
HUB_INBOX_ADDRESS=0x000000000000000000000000...

# SoulboundReceiver address (enables cross-chain soulbound minting)
SOULBOUND_RECEIVER=0x...
```

:::danger
Use `cast to-uint256`, which **left**-pads. Do **not** use `cast to-bytes32` — it **right**-pads,
producing a valid-looking bytes32 that decodes to the wrong recipient:

```
address            0x1234…cdef
cast to-uint256    0x0000000000000000000000001234…cdef   ✅ correct
cast to-bytes32    0x1234…cdef000000000000000000000000   ❌ wrong recipient
```

Cross-chain recipients are `bytes32` left-padded addresses, which is how Hyperlane delivers
them. `SpokeRegistry.hubInbox` is timelocked after `completeSetup()`, so a right-padded value
pasted here cannot be corrected once you finalize in Step 5.
:::

Then deploy:

```bash
pnpm deploy:testnet:spoke
```

This deploys HyperlaneAdapter, SpokeRegistry, and SpokeSoulboundForwarder to OP Sepolia.

## Step 4: Configure Trust on Hub

The hub needs to trust the spoke's HyperlaneAdapter. Replace the placeholder addresses with your actual deployed addresses:

:::danger
Same padding rule as Step 3, and here it fails silently. Hyperlane delivers `_sender` as a
**left**-padded address and `CrossChainInbox.handle` compares it directly against
`trustedSources[origin][sender]`. A right-padded value never matches, so every cross-chain
message reverts as untrusted — and because Step 6 checks `trustedSources` with the _same_
wrong bytes32, verification returns `true` while the bridge is dead.
:::

```bash
source .env.testnet

# Get the adapter's LEFT-padded bytes32 representation (NOT cast to-bytes32 — see above)
ADAPTER_BYTES32=$(cast to-uint256 0x<SPOKE_HYPERLANE_ADAPTER>)

# CrossChainInbox: trust the spoke's adapter
cast send <CROSS_CHAIN_INBOX> \
  "setTrustedSource(uint32,bytes32,bool)" \
  11155420 $ADAPTER_BYTES32 true \
  --rpc-url $BASE_SEPOLIA_RPC --private-key $PRIVATE_KEY

# SoulboundReceiver: trust the spoke's adapter
cast send <SOULBOUND_RECEIVER> \
  "setTrustedForwarder(uint32,address)" \
  11155420 0x<SPOKE_HYPERLANE_ADAPTER> \
  --rpc-url $BASE_SEPOLIA_RPC --private-key $PRIVATE_KEY
```

## Step 5: Finalize Setup (both chains) — required

Several contracts use `TimelockOwnable`, which starts in a **setup mode** where the owner can
configure them with immediate one-transaction calls. Finalizing ends setup mode and puts every
subsequent privileged change behind the propose/activate timelock. **A deployment that is
never finalized keeps its owner key as a single-transaction kill switch** — on the spoke that
means the HyperlaneAdapter's dispatch allowlist (the control that stops an arbitrary caller
forging cross-chain registrations) can be reopened instantly and forever.

There are two finalize steps, because the timelocked contracts live on **both** chains — the
hub registries and operator infrastructure on Base Sepolia, and HyperlaneAdapter +
SpokeRegistry on OP Sepolia. Running only the hub one leaves the spoke unprotected.

Check what would change first, then finalize:

```bash
cd packages/contracts

pnpm verify:setup:testnet:hub     # dry read of hub setup state
pnpm finalize:testnet:hub         # ends setup mode on Base Sepolia

pnpm verify:setup:testnet:spoke   # dry read of spoke setup state
pnpm finalize:testnet:spoke       # ends setup mode on OP Sepolia
```

:::warning
Run this **after** Step 4. Once setup mode is closed, the trust-configuration calls above are
timelocked, so wiring anything you forgot means waiting out the delay.
:::

## Step 6: Verify Everything Works

```bash
source .env.testnet

# Hub: check registries are wired
cast call <FRAUD_REGISTRY_HUB> "walletRegistry()(address)" --rpc-url $BASE_SEPOLIA_RPC

# Spoke: check hub chain ID
cast call <SPOKE_REGISTRY> "hubChainId()(uint32)" --rpc-url $OPTIMISM_SEPOLIA_RPC

# Trust: check adapter is trusted
# NOTE: this only proves the value you SET is the value stored. It cannot tell you the
# padding was right — see the Step 4 warning. A right-padded adapter reads back `true` here
# and still fails on every delivery.
cast call <CROSS_CHAIN_INBOX> "trustedSources(uint32,bytes32)(bool)" \
  11155420 $ADAPTER_BYTES32 --rpc-url $BASE_SEPOLIA_RPC

# FeeManager: check the Chainlink feed resolves (price in USD cents)
cast call <FEE_MANAGER> "getEthPriceUsdCentsView()(uint256)" --rpc-url $BASE_SEPOLIA_RPC

# FeeManager: the fee a user would actually pay, in wei
cast call <FEE_MANAGER> "currentFeeWei()(uint256)" --rpc-url $BASE_SEPOLIA_RPC
```

:::info
`getEthPriceUsdCentsView()` degrades to the stored fallback price when the oracle is
unavailable, stale, or out of bounds, so a plausible number here is not by itself proof the
Chainlink feed is live. Compare it against the real ETH price — if it reads exactly
`fallbackEthPriceUsdCents`, the feed is not being used.
:::

## Step 7: Update Chain Config

Fill deployed addresses into `@swr/chains` so the frontend knows where the contracts live:

**`packages/chains/src/networks/base-sepolia.ts`** — Fill all `hubContracts` fields.

**`packages/chains/src/networks/optimism-sepolia.ts`** — Fill all `spokeContracts` fields.

Then rebuild and push to trigger a Vercel redeploy:

```bash
pnpm build
```

## Troubleshooting

**"PRIVATE_KEY required for non-local deployments"** — Make sure `.env.testnet` has `PRIVATE_KEY` set and you ran `source .env.testnet` before the deploy command.

**"insufficient funds"** — Get more testnet ETH from the faucets above.

**Verification fails** — This is non-blocking. Contracts are deployed even if verification fails. You can verify later with `forge verify-contract`.
